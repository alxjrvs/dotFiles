# agent-vault.txt — the items in the `claude-agent` 1Password vault that THIS REPO
# RESOLVES (or whatever `BOOM_vault` names).
#
# Checked by `op-agent audit agent-vault.txt`, wired as a `boom verify` step, in
# ONE direction: every item named here must exist in the vault. A declared item
# that is missing means a consumer in this repo is about to resolve nothing, and
# that is a real breakage worth failing a verify over.
#
# NOT AN INVENTORY. An item in the vault that this file does not name is fine.
# The reverse check used to fail too, on the reasoning that anything the service
# account can read is blast radius somebody should have reviewed. That reasoning
# is sound and the control was still wrong: it made the vault effectively
# read-only, because adding or retiring a credential failed `boom verify` until
# this file was edited in the same breath. A vault is a place to keep things.
# Putting something in it is not drift.
#
# What the vault's own properties do and don't get you, since the argument above
# was built on them:
#
#   1. Service-account vault access is IMMUTABLE after creation. 1Password: "If
#      you want to grant a service account access to additional vaults or
#      Environments … you'll need to create a new service account." Scope can
#      never be tightened in place — only the vault's CONTENTS can change. So
#      membership IS the lever; this file simply no longer pulls it automatically.
#   2. This is an Individual/Family account, so there is no Activity Log and no
#      service-account usage report (both Business/Teams only). There is no
#      per-item record of what the SA read, and that gap is deliberately
#      accepted (2026-08-19).
#
# Keeping the vault small is therefore still worth doing. It is now a judgement
# made when you put something in, rather than a gate that fails a machine check.
#
# RULES
#   - kebab-case only, `^[a-z0-9]+(-[a-z0-9]+)*$`, FOR THE TITLES LISTED HERE.
#     Every op:// ref is re-parsed by `sh -c`, so a space word-splits and the
#     resolve fails silently — the bug that took down two MCP servers on
#     2026-07-25. That is a property of items this repo resolves; an item nobody
#     references can keep whatever 1Password's new-item dialog called it.
#   - One title per line. Trailing `#` comments are stripped.
#   - An entry earns its place by having a NAMED CONSUMER, and this is now
#     ENFORCED, not merely asserted: `op-agent audit` fails when a declared item
#     has no `op://` resolution reference anywhere in this repo. It was prose
#     until `render-api-key` sat here naming a `render` MCP server that existed
#     in no scope, passing every audit, because membership and casing were all
#     that was checked. There is no "probably useful later" tier — that is how
#     this vault once grew to four times the items actually in use.
#
# STATE: sharply reduced on 2026-08-19. The removed items were MOVED, not
# deleted, into `Archive`, `Projects`, `Binfinite` and `Gnar`. None had a
# consumer on this machine, so the service account's reach shrank by most of its
# former size with nothing to re-point and no new service account required: SA
# access is granted per VAULT, so removing an item from the vault removes it
# from the agent's reach immediately. That is also why this file is the control
# — scope was fixed at creation and cannot be narrowed, but membership can.
#
# Every line below is a credential this machine actually resolves. Adding one
# means naming what resolves it, in the comment, in the same commit.

gninety                   # NINETY_API_TOKEN_COMMAND in dot-claude/settings.json
